# 局域网聊天室 · 应用层协议 v1

> **状态：已冻结（tag `proto-v1`）**　·　2026-10-23
> 帧格式：8 字节定长首部 + UTF-8 JSON 体　·　17 种消息类型　·　15 个错误码
>
> 本文件是唯一事实源。任何字段、类型码、错误码的改动都必须走同一条链路：
> **改本文档 → 升 `ver`（不兼容时）→ 同步 `shared/protocol.py`、服务端、客户端 → 重新打 tag**。
> 代码与本文档冲突时，以本文档为准；确实要改，先改文档。

## 0　三条纪律

1. **不猜默认值。** 必填字段缺失一律回 `2003` 并丢弃该帧，不做「缺省补齐」——那会把前端的 bug 变成服务端的静默错误。
2. **先验长度，再解析。** `length` 超过上限立刻断开，绝不按谎报的长度分配内存。
3. **报文体永远是 JSON 对象。** 不是数组、不是裸字符串；没有内容就写 `{}`。

## 1　传输层约定

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 传输协议 | TCP | 长连接，一条连接承载全部业务 |
| 服务端端口 | 8888（可用 `--port` 改） | 客户端用系统分配的临时端口 |
| 字符编码 | UTF-8（无 BOM） | JSON 必须 `ensure_ascii=False`，否则中文变成 `\uXXXX` 六个字节，长度全错 |
| 时间 | UTC 秒级整数 | 展示时再转本地时区，避免多机时区不一致 |
| 单帧上限 | 65536 字节 | 含 8 字节首部 |
| 正文上限 | 8192 字节 | 仅约束 `CHAT_GROUP` / `CHAT_PRIVATE` 的 `text`，按 UTF-8 字节算 |
| 登录时限 | 10 s | 连接建立后 10 s 内未完成登录，服务端关闭连接 |

## 2　帧格式

```
偏移    0     1     2     3     4     5     6     7     8 ──────────►
     ┌───────────┬─────┬─────┬───────────────────────┬────────────────────┐
     │ magic 2B  │ ver │type │   length 4B（大端）    │  body（length 字节）│
     │ 0x43 0x48 │0x01 │0x10 │ 0x00 0x00 0x00 0x2C   │  {"msg_id":…}       │
     └───────────┴─────┴─────┴───────────────────────┴────────────────────┘
```

| 字段 | 长度 | 取值 | 违规时怎么办 |
| --- | --- | --- | --- |
| `magic` | 2 B | 固定 `0x4348`（ASCII `"CH"`） | 不匹配 → **立即关闭，不回包**（防误连与端口扫描） |
| `ver` | 1 B | 协议版本，当前 `1` | 不匹配 → 回 `ERROR(1003)` 后关闭 |
| `type` | 1 B | 消息类型码，见第 3 章 | 未知 → 回 `ERROR(2004)`，**连接保持** |
| `length` | 4 B | 报文体字节数，**大端序**；上限 65528（整帧 ≤ 65536 含 8 字节首部） | 超过 65528 → 不回包直接关闭（流已不可信） |
| `body` | `length` B | JSON 对象，UTF-8 | 解析失败 → `ERROR(2003)`，容错一次；连续两次断开 |

**为什么用大端**：网络字节序统一大端。Python 里 `struct.Struct(">HBBI")` 的 `>` 就是大端；换到 x86 小端环境或与 C 程序对接时，不改这一个字符就会解析错位。

## 3　消息类型总表（17 种）

| 类型码 | 名称 | 方向 | 用途 | 必填字段 |
| --- | --- | --- | --- | --- |
| `0x01` | LOGIN_REQ | C→S | 登录 / 断线续会话 | `username` `client_ver` + (`pwd_hash` 或 `token`) |
| `0x02` | LOGIN_RESP | S→C | 登录结果 | `code` |
| `0x03` | LOGOUT | C→S | 主动退出 | — |
| `0x10` | CHAT_GROUP | C→S→C | 群聊 | `msg_id` `text` |
| `0x11` | CHAT_PRIVATE | C→S→C | 私聊 | `msg_id` `to` `text` |
| `0x12` | CHAT_SYSTEM | S→C | 系统通知（上下线 / 被踢 / 公告） | `text` `level` `ts` |
| `0x20` | USER_LIST | S→C | 全量在线名单 | `users` |
| `0x21` | USER_JOIN | S→C | 有人上线 | `user_id` `username` `since` |
| `0x22` | USER_LEAVE | S→C | 有人下线 | `user_id` `username` `reason` |
| `0x30` | PING | C→S | 心跳请求 | — |
| `0x31` | PONG | S→C | 心跳应答 | `server_time` |
| `0x40` | FILE_OFFER | C→S→C | 文件传输请求 | `transfer_id` `to` `name` `size` `sha256` |
| `0x41` | FILE_ACCEPT | C→S→C | 接收方同意 / 拒绝 | `transfer_id` `accept` |
| `0x42` | FILE_CHUNK | C→S→C | 数据块 | `transfer_id` `offset` `data` |
| `0x43` | FILE_DONE | C→S→C | 传输结束 + 校验结果 | `transfer_id`（发送方带 `sha256`，接收方带 `ok`） |
| `0x50` | ERROR | S→C | 错误（登录后） | `code` `message` |
| `0x60` | ACK | S→C | 消息回执 | `msg_id` `seq` |

> 方向 `C→S→C` 表示「客户端发给服务端，服务端补字段后转发给一个或多个客户端」。

## 4　字段定义

### 4.1 公共字段

| 字段 | 类型 | 谁生成 | 说明 |
| --- | --- | --- | --- |
| `msg_id` | string | 客户端 | 格式 `用户名-6位序号`，如 `alice-000123`。服务端**原样透传**，只用于去重与 ACK 关联 |
| `seq` | int | 服务端 | 全局单调递增，从 1 开始。断点续传、排序、去重全靠它 |
| `ts` | int | 客户端 | 客户端 UTC 秒；仅用于展示，服务端不信任 |
| `server_ts` | int | 服务端 | 服务端 UTC 秒，权威时间 |
| `code` | int | 服务端 | 错误码，见第 5 章 |
| `reason` | string | 服务端 | `logout` / `timeout` / `kicked` |
| `level` | string | 服务端 | `info` / `warn` |
| `transfer_id` | string | 发送方 | 本次传输的唯一标识，16 位十六进制 |

### 4.2 会话（0x01—0x03）

**LOGIN_REQ（0x01，C→S）**

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `username` | string | 是 | 1—16 字符，`^[A-Za-z0-9_\u4e00-\u9fa5]{1,16}$`（中英文、数字、下划线） |
| `pwd_hash` | string | 二选一 | 明文口令的 SHA-256，64 位小写十六进制 |
| `token` | string | 二选一 | 上次登录拿到的 `session_token`，32 位十六进制；**带 token 时忽略 `pwd_hash`** |
| `client_ver` | string | 是 | 客户端版本，如 `"1.0"`；与服务端不一致时回 `1003` |
| `resume_seq` | int | 否 | 客户端已处理的最大 `seq`；存在则补发 `seq > resume_seq` 的消息 |

**LOGIN_RESP（0x02，S→C）**

| 字段 | 类型 | 何时出现 | 说明 |
| --- | --- | --- | --- |
| `code` | int | 总是 | `0` 成功；非 0 见第 5 章 |
| `message` | string | 失败时 | 中文原因，客户端可直接展示 |
| `user_id` | int | 成功时 | 服务端分配的用户编号 |
| `username` | string | 成功时 | 规范化后的昵称（回显） |
| `session_token` | string | 成功时 | 32 位十六进制，断线重连凭据 |
| `server_time` | int | 成功时 | 服务端 UTC 秒 |

> **登录阶段的一切失败都走 `LOGIN_RESP{code≠0}` 然后关闭连接**，不发 `ERROR`。登录成功之后才用 `ERROR`。
> 这样客户端只需要在一个地方等登录结果。

**LOGOUT（0x03，C→S）**：空体 `{}`。服务端广播 `USER_LEAVE{reason:"logout"}` 后关闭。

### 4.3 聊天（0x10—0x12）

**CHAT_GROUP（0x10）**

| 字段 | 类型 | 发送方填 | 服务端补 |
| --- | --- | --- | --- |
| `msg_id` | string | 是 | 透传 |
| `text` | string | 是 | — |
| `ts` | int | 可选 | — |
| `seq` | int | — | 是（分配后写入） |
| `from` | string | — | 是（**服务端补，不信任客户端**） |
| `server_ts` | int | — | 是 |

**CHAT_PRIVATE（0x11）**：同上，另加 `to`（string，接收者昵称，发送方必填）。服务端按 `to` 单投给接收者，并回显一份给发送者。

**CHAT_SYSTEM（0x12，S→C）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `text` | string | 如「alice 已离线（超时）」 |
| `level` | string | `info` / `warn` |
| `ts` | int | 服务端时间 |
| `reason` | string | 可选：`logout` / `timeout` / `kicked` / `announce` |

### 4.4 在线状态（0x20—0x22）

**USER_LIST（0x20）**：`users` 为数组，每项 `{user_id, username, since}`；`count` 为人数。
登录成功后**立即**下发全量，客户端据此重建列表（此前状态全部作废）。

**USER_JOIN（0x21）**：`{user_id, username, since}`，广播给**除本人外**的所有人。

**USER_LEAVE（0x22）**：`{user_id, username, reason}`，同上。缺了「除本人外」这一条，自己会收到自己的上下线通知，界面上就是两条重复的系统消息。

### 4.5 心跳（0x30—0x31）

**PING（0x30）**：空体 `{}`。**PONG（0x31）**：`{server_time}`。

- 客户端每 15 s 发一次；
- 服务端收到**任何**帧都刷新 `last_active`（不只是 PING，否则活跃用户会被误杀）；
- 服务端每 5 s 扫描一次，`now - last_active > 45` 即判死，广播 `USER_LEAVE{reason:"timeout"}` 后关闭。

### 4.6 文件（0x40—0x43）

**FILE_OFFER（0x40）**：`{transfer_id, to, name, size, sha256}`
`size ≤ 52428800`（50 MB）；`name` 由接收方净化（只取 basename，拒绝 `..`、`/`、`\`、Windows 保留名）。

**FILE_ACCEPT（0x41）**：`{transfer_id, accept}`；拒绝时附 `reason`。接收方在弹窗里点「接收」才发。

**FILE_CHUNK（0x42）**：`{transfer_id, offset, data}`
`data` 是原始字节的 Base64，**每块 32 KB 原始数据**（编码后约 43.7 KB，仍在 64 KB 帧内）。
`offset` 必须严格等于已接收字节数，跳号即中断（回 `3003`）。

**FILE_DONE（0x43）**：
发送方 → 接收方：`{transfer_id, sha256}`（整文件摘要）；
接收方 → 发送方：`{transfer_id, ok, sha256}`。`ok=false` 时附 `reason`（`hash_mismatch` / `cancelled` / `timeout`）。

### 4.7 控制（0x50、0x60）

**ERROR（0x50，S→C）**：`{code, message}`，可选 `ref_msg_id` 指向触发它的那条消息。

**ACK（0x60，S→C）**：`{msg_id, seq}`。服务端**先回 ACK，再扇出**——顺序反了，客户端会先看到消息再看到回执，状态机就对不上。

## 5　错误码表

| 码 | 含义 | 客户端提示文案 | 连接 |
| --- | --- | --- | --- |
| `1001` | 昵称已被占用 | 该昵称已有人使用，请换一个 | 断开 |
| `1002` | 口令错误 / 失败次数过多 | 口令不正确，还可尝试 N 次 | 断开 |
| `1003` | 协议版本不符 | 客户端版本过旧，请更新后再连接 | 断开 |
| `1004` | 昵称格式非法 | 昵称需 1—16 个字符，仅支持中英文、数字与下划线 | 断开 |
| `1005` | 会话已失效 | 登录已过期，请重新登录 | 断开 |
| `1006` | 未登录就发了业务帧 | 请先登录 | 断开 |
| `2001` | 消息过长 | 消息超过 8192 字节，请分段发送 | 保持 |
| `2002` | 发送过于频繁 | 发送太快了，请稍后再试 | 保持 |
| `2003` | 报文格式错误 | 客户端数据异常，请重启客户端 | 保持（容错一次） |
| `2004` | 未知消息类型 | 客户端与服务端版本不匹配 | 保持 |
| `3001` | 目标用户不在线 | 对方不在线，消息已暂存 | 保持 |
| `3002` | 文件过大 / 并发超限 | 文件超过 50 MB 或同时传输过多 | 保持 |
| `3003` | 传输超时或已取消 | 传输中断，可重新发送 | 保持 |
| `4001` | 被管理员移除 | 你已被管理员移出聊天室 | 断开 |
| `5001` | 服务端内部错误 | 服务器开小差了，请稍后重连 | 保持 |

> `1005`、`1006` 是本版为断线续会话补充的码，其余 13 个沿用《功能拆解》附录 A。

## 6　连接状态机

```
          TCP 握手完成
                │
                ▼
          ┌───────────┐   收到业务帧（非 LOGIN）→ ERROR(1006) 并关闭
          │ CONNECTED │   10 s 内未收到 LOGIN_REQ → 直接关闭
          └─────┬─────┘
                │ LOGIN_REQ 校验通过
                ▼
          ┌───────────┐   任意帧刷新 last_active；45 s 无帧 → 判死
          │  AUTHED   │
          └─────┬─────┘
                │ LOGOUT / 认证失败 / 超时 / 被踢
                ▼
          ┌───────────┐
          │  CLOSING  │ → CLOSED
          └───────────┘
```

CONNECTED 状态下只接受 `0x01` 与 `0x30`；其余一律 `1006`。

## 7　关键时序

### 7.1 登录

```
客户端                                      服务端
  │ ─── TCP 三次握手 ───────────────────────►│  CONNECTED（10 s 计时开始）
  │ ─── 0x01 LOGIN_REQ ─────────────────────►│  拆帧 → 校验昵称格式 → 是否在线占用
  │     {username, pwd_hash, client_ver}     │  → 口令校验（首次登录则建号）
  │◄── 0x02 LOGIN_RESP {code:0, user_id,    │  双索引写表（clients / names）
  │      session_token, server_time}         │
  │◄── 0x20 USER_LIST {users:[…], count}     │  先给本人全量名单
  │                                          │ ─── 0x21 USER_JOIN ──► 其他人
失败分支：
  │◄── 0x02 LOGIN_RESP {code:1001, message}  │  随后关闭连接
```

### 7.2 群聊

```
A ──0x10 CHAT_GROUP{msg_id, text}──► S
S: 校验长度（≤8192 B）与频率（≤10 条/s）→ 分配 seq
S ──0x60 ACK{msg_id, seq}──► A                      先回执
S ──0x10 CHAT_GROUP{msg_id, seq, from, text, server_ts}──► A、B、C（含发送者）
失败分支：
  超长 → 0x50 ERROR{2001} 只回 A，不扇出
  超频 → 0x50 ERROR{2002} 只回 A，不扇出
```

### 7.3 私聊与离线补发

```
在线：
A ──0x11{msg_id, to:"bob", text}──► S ──0x11{…, from:"alice", seq}──► B
                                     └──0x60 ACK{msg_id, seq}────────► A
                                    （同时把补全后的帧回显给 A，双方渲染同一份数据）

离线：
A ──0x11{to:"bob"}──► S: bob 不在线 → offline[bob].append(msg)（每人上限 200 条）
S ──0x50 ERROR{3001, "对方不在线，消息已暂存"}──► A

B 上线：
S ──0x02 LOGIN_RESP(ok)──► B ──0x20 USER_LIST──► B ──按 seq 升序补发──► B
补发完成后立即清空 offline[bob]，否则每次重连都重发一遍（最常见的刷屏 bug）
```

### 7.4 文件传输

```
A ──0x40 FILE_OFFER{transfer_id, to:"bob", name, size, sha256}──► S ──► B
B ──0x41 FILE_ACCEPT{transfer_id, accept:true}──► S ──► A
A ──0x42 FILE_CHUNK{transfer_id, offset:0, data:…}──► S ──► B     ← 32 KB 一块，循环
A ──0x43 FILE_DONE{transfer_id, sha256}──► S ──► B
B: 写 bob.part → 校验 SHA-256 → 一致才改名
B ──0x43 FILE_DONE{transfer_id, ok:true}──► S ──► A
失败分支：
  30 s 没有新块 → 双方回 3003，清理会话与 .part
  offset 跳号 → 中断，回 3003
```

### 7.5 心跳与断线重连

```
C ──0x30 PING──► S ──0x31 PONG{server_time}──► C          每 15 s
S: 每 5 s 扫描，now - last_active > 45 → 关闭 + 广播 USER_LEAVE{reason:"timeout"}

C: 连续 3 次没有 PONG → 判定断线（单次超时不算，网络抖动很常见）
C: 退避 1、2、4、8、16、30 s（±20% 抖动，最多 10 次）
C ──0x01 LOGIN_REQ{username, token, resume_seq:last_seq}──► S
S: 校验 token → 若同 user 的旧连接还在，关掉旧连接、由新连接接管（不广播上下线）
S ──0x02 LOGIN_RESP(ok)──► C ──0x20 USER_LIST──► C ──补发 seq > resume_seq──► C
```

## 8　参数与上限

| 参数 | 取值 | 依据 |
| --- | --- | --- |
| 心跳间隔 / 判死时间 | 15 s / 45 s | 超时 ≥ 3 × 心跳，容忍偶发丢包；且小于 NAT 会话超时（30—60 s） |
| 心跳扫描周期 | 5 s | 判死误差 ≤ 5 s |
| 单帧上限 | 65536 B（含 8 B 首部，报文体 ≤ 65528） | 64 KB |
| 正文上限 | 8192 B | 单条文本 |
| 发送限流 | 10 条/秒（滑动窗口） | 超限回 2002 |
| 离线队列 | 每人 200 条 | 超出丢最旧并记 WARN |
| 重连退避 | 1/2/4/8/16/30 s，±20%，最多 10 次 | 抖动避免 50 个客户端同一秒重连 |
| 文件大小 / 分块 | 50 MB / 32 KB | 块远大于 MTU，由 TCP 分段而不是 IP 分片 |
| 文件并发 / 空闲超时 | 每人 2 个 / 30 s | 超时清理会话与临时文件 |
| 登录时限 | 10 s | 防占位连接 |
| 口令失败锁定 | 5 次 / 60 s | 防在线暴力破解 |
| 昵称长度 | 1—16 字符 | 中英文、数字、下划线 |

## 附录 A　LOGIN_REQ 逐字节拆解（标准答案）

口令 `123456`，昵称 `alice`，客户端版本 `1.0`。明文口令先做一次 SHA-256：

```
8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92
```

报文体（紧凑 JSON，`ensure_ascii=False`，共 **132** 字节）：


## 附录 B　扩展规则

1. **加可选字段**：`ver` 不变，接收方忽略不认识的字段，但**必填字段仍然必须校验**。
2. **加必填字段或改语义**：`ver` 升到 2，服务端对 `ver=1` 的客户端回 `1003`。
3. **加新类型码**：不得复用已废弃的码；新码必须在第 3 章登记后才允许写代码。
4. **不允许**在 `body` 里塞二进制；文件走 Base64 分块，或另立 `ver=2` 的二进制帧。
